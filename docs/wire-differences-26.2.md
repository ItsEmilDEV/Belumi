# Minecraft 26.2 vs 26.3 on the wire

Belumi's codecs implement 26.3 (protocol 777). A 26.2 server (protocol 776) is served by a translation layer in
`crates/horizon-client/src/net/protocol_compat.rs` and, for registry ids, by the dialect switch in
`crates/horizon-protocol/src/dialect.rs`. Only differences verified against a real 26.2 server are translated;
everything else uses the native codec.

Two kinds of difference exist:

1. Layout and id changes of packets, handled by rewriting the packet body or its id at the connection boundary.
2. Registry ids that moved (items, blocks, entity types, data components, particles, sounds, ...), handled by tables
   generated by name, never by position.

## Detecting differences

`tools/diff_26_2_codecs.sh JAR_26_2 JAR_26_3 OUT_DIR` decompiles the network classes of both server jars with `javap`
and lists them: `SHAPE` means fields or signatures differ (look at these), `CODE` is usually a refactor.
The data generator reports (`java -DbundlerMainClass=net.minecraft.data.Main -jar server.jar --reports`) provide
`registries.json`, `blocks.json` and `packets.json`.

## Selecting the protocol

`--protocol auto|native|<number>` (default `auto`) pings the server and picks 776 or 777. The developer variable
`BELUMI_TARGET_PROTOCOL` overrides it. An unknown version is an error until its packets are implemented; it never
falls back to native silently.

## Packet ids

Clientbound Play: 26.3 inserted three packets in front of otherwise identical ones, so every 26.2 id from the
insertion point is shifted by one more each time:

- `add_transient_block` before 26.2 id 37 (`forget_level_chunk`)
- `post_effects` before 26.2 id 82 (`respawn`)
- `swing_animation` before 26.2 id 121 (`system_chat`)

Serverbound Play: 26.3 inserts the empty `Punch` packet at id 46; 26.2 calls the same action `Swing` and appends the
hand. The remaining 26.2 ids from 47 to 63 are one lower. Configuration ids are the same. Verified from the 26.2
server's `GameProtocols` registration order and a live packet capture.

## Clientbound payload rewrites

| Packet | 26.2 form | Translation |
|---|---|---|
| Login, Respawn | `previousGameType` is a nullable byte (`0xff` none); Respawn then carries `data_to_keep` | optional VarInt of 26.3 |
| Explode | always plays its sound | append the `play_sound` byte |
| AddEntity | `kind` is a 26.2 `entity_type` id | map by name |
| UpdateTags | entity type, block and item tags list 26.2 ids | map each id |
| BlockUpdate, SectionBlocksUpdate | 26.2 block state ids (section entry is `state << 12 \| position`) | map states |
| LevelEvent | type 2001 (block break) carries a block state | map the state |
| Chunk data | block state palettes; a direct palette is 15 bits in 26.2 and 16 in 26.3 | re-encode with 26.3 ids |
| LevelParticles | flags and position first, one `maxSpeed`, `count` as Int, particle last | 26.3 layout: particle first, three speeds, count, randomization 0. The particle bytes are passed through untouched because the dialect-aware decoder translates them once |
| AwardStats | the value id is a registry id of the stat's type: `mined` blocks, `crafted`/`used`/`broken`/`picked_up`/`dropped` items, `killed`/`killed_by` entity types, `custom` stats | map by type |
| Animate | 0 swing main hand, 2 wake up, 3 swing off hand, 4 critical, 5 magic critical | 26.3 keeps wake up (0), critical (1), magic critical (2); swings become the separate `SwingAnimation` packet |
| Recipe book additions | tag slot displays carry a bare resource location | `HolderSet` of 26.3 |
| Advancements | `DisplayInfo` carries x/y position | 26.3 sends the position after the requirements |
| EntityPositionSync | `PositionMoveRotation` (position, delta movement, yaw, pitch) then `on_ground` | `PositionPath` (linear: type 0 and end position), yaw, pitch, `on_ground`; delta movement is not sent |
| MoveEntity (Pos, PosRot, Rot) | raw deltas, optional rotation, trailing `on_ground` | `on_ground` and the step count are packed into a VarInt properties field; Rot-only moves `on_ground` before the rotation |

## Serverbound rewrites

| Packet | Difference | Translation |
|---|---|---|
| PlayerAction | 26.3 inserted `CHANGE_DESTROY_DIRECTION` at action 1, later actions are one higher | `0, 1` become `0` (start at the new position), `n` becomes `n - 1`. Without it a released click reads as "finish destroying" |
| Punch | 26.2 `Swing` with a hand | send `Swing` with hand 0 |
| AcceptTeleportation | 26.3 added position and rotation | send only the teleport id |
| SignUpdate | 26.3: position, four lines, side as VarInt; 26.2: position, side as boolean, four lines | reorder; without it the server drops the connection when a sign editor closes |

Checked and identical (no translation): chat packets (only `Optional` refactors), entity data serializer ids (26.3
appends `DYE_COLOR`), heightmap types, `OpenSignEditor` (boolean byte equals VarInt 0/1), `MoveVehicle`, `UseItem`,
`UseItemOn`, `CommandSuggestion`, the structure block rotation, and the wire enums: pose, equipment slot, game
type, difficulty, boss bar, click type and others.

## Dialect (registry ids)

`dialect::set_26_2` is switched on by the network thread when the connection uses 26.2 and off for native
connections. The codecs that carry registry ids translate in both directions through generated tables:
items, data components (by kind), particles, sounds, command argument types, block states in entity metadata, and
item stacks inside slots, hashed slots, templates and recipes. Everything held in memory stays in 26.3 ids.

Rewriters must not translate ids that a dialect-aware decoder translates again (double translation). The data component
`pot_decorations` is the only component layout known to differ: a list of item ids in 26.2.

Regenerate the tables whenever either jar changes:

```sh
tools/gen_26_2_ids.py REPORTS_26_2 REPORTS_26_3 vendor/horizon/crates/horizon-protocol/src/dialect_26_2.rs
```

## Testing a translation

Run a local 26.2 server with a console FIFO, start the client with `--control-socket` and
`BELUMI_DUMP_BAD_PACKETS=DIR`, and drive it with `horizon-ctl command ...` (`/give`, `/summon`, `/particle`,
`/setblock`, signs, teams). Every packet that does not decode is written to `DIR` with its original bytes.
`HORIZON_NET_DEBUG=1` logs the packet flow.
